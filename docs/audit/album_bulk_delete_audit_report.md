  - **FR-DEL-003（一括削除・確認モーダル）**: 1件以上選択時に削除ボタンが活性化し、専用確認モーダル（`modal-delete-confirm`）が表示される。モーダル内に削除対象アルバム一覧、削除曲数集計警告、取消不可の警告文が明記されていることを確認。

  - **FR-DEL-005（カスケード削除・アトミック実行）**: スプレッドシートから該当アルバムの全トラック行が漏れなく一括削除され、`LockService` による排他制御が行われていることを確認。

### 2.2 システムアーキテクチャへの準拠状況: 【完全準拠 (100%)】
- **ADR-DEL-001（アトミック一括置換方式）**:
  行ごとの個別削除（`deleteRow` ループ）を排除し、全行取得 → メモリ除外 → `clearContent()` → 残存行一括 `setValues()` により、GAS API呼び出し回数を3回に最少化。残存0行時の `setValues([])` 例外発生を回避するヘッダー保護ガード（`if (retainedRows.length > 0)`）が実装されていることを確認。
- **ADR-DEL-002（Google Drive画像ファイルの保持方針）**:
  スプレッドシートの行参照のみを解除し、Drive上の実ファイル削除APIは呼び出さない設計を厳守。誤削除時のバージョン履歴からの完全復元性および同一画像URLの他アルバム共有破壊防止が担保されていることを確認。
- **ADR-DEL-003（選択モードトグル方式）**:
  通常時の軽快なドリルダウン操作と視覚的鑑賞体験を損なわず、安全かつ快適に複数選択が行えるUIモデルが実現されていることを確認。
- **ADR-DEL-004（複合キー仕様: `albumArtist` + `albumName`）**:
  既存の1トラック1行フラット構造および `updateAlbumBatch` の規約と整合した正規化複合キー（`${trim(albumArtist)}:::${trim(albumName)}`）を採用し、既存データとの完全互換性を維持していることを確認。
- **ADR-DEL-005（削除後の画面自動フォールバック制御）**:
  削除対象に表示中アルバムが含まれていた場合のSTEP 3クリア、全アルバム削除時のアーティスト消滅および安全な画面復帰（モバイル: STEP 1、PC: 先頭アーティスト自動選択）が仕様通りに実装されていることを確認。

  不必要な新フレームワークや外部ライブラリを導入せず、既存プロジェクトのバニラJavaScript (ES6+)、Tailwind CSS、GAS標準サービスの規約を忠実に踏襲しています。
- **ドキュメント・コメントの完全性**:
  すべての新設・改修メソッドにJSDoc形式の型定義・説明コメントが付与されており、引数・戻り値・事前条件が明確です。プレースホルダー（`// TODO`, `// 省略` 等）は一切存在しません。

### 3.2 結合度と凝集度
- 各レイヤー間のインターフェースがデータオブジェクト（`DeleteAlbumsPayload`, `DeleteAlbumsResult`, `ApiResponse`）を介して疎結合に保たれています。
- フロントエンドは内部キャッシュ（`Store.state.allTracks`）とツリー再構築関数（`buildCatalog`）を活用することで、サーバー通信後の冗長な再フェッチ（`apiGetAllData`）を不要とし、高い自律性と凝集度を保っています。

### 3.3 エラーハンドリング・セキュリティ
- **サーバーサイド二重バリデーション**:
  `MusicService.validateDeletePayload_` において、`payload` がオブジェクトであること、`payload.albums` が配列かつ1件以上であること、各要素がオブジェクトであり、トリム後の `albumArtist` および `albumName` が空文字でなく255文字以内であることを厳格に検証し、不正時は `VALIDATION_FAILED` 例外を送出しています。
- **スプレッドシート数式インジェクション（Formula Injection）防御の維持**:
  残存データ行を一括書き戻す際、既にエスケープ済みのデータ文字列（`'=...`）が損なわれることなく保持され、データ破損が発生しないことをテストにて実証確認しました。
- **XSS防御**:
  モーダル内のアルバム名・アーティスト名表示、およびカード再描画において `Utils.escapeHtml` が徹底して適用されており、スクリプト混入の危険性を排除しています。
- **二重送信・並行性制御（Race Condition防止）**:
  - クライアント側: `this.isDeletingAlbums` フラグにより多重呼び出しをガード。削除実行開始時に確定ボタン、キャンセルボタン、閉じるボタンを即座に `disabled = true` とし、スピナーアニメーションを表示。
  - 削除通信待機中は Escキーや背景クリックによるモーダルクローズを遮断（BUG-002是正）。
  - サーバー側: `LockService.getScriptLock().tryLock(10000)` により他ユーザーとの競合を防止し、`finally` で確実にロックを解放。
- **モバイル操作性・アクセシビリティ (WCAG 2.1 AA)**:
  - 新設されたすべてのボタン（選択切替、全選択、全解除、一括削除、個別削除、モーダル確定、キャンセル、閉じる）が最小 44px × 44px のタップ領域を確保。
  - 削除確認フォームに `onsubmit="event.preventDefault();"` を付与し、Enterキー誤押下による不正リロードや誤送信を確実に防止。
  - 選択切替ボタンに `aria-pressed`, `aria-label`, `title` 属性を付与し、支援技術に対する状態通知を担保（BUG-003是正）。

### 3.5 長期的運用リスク・技術的負債
- **Google Drive上の孤立ファイル蓄積**:
  - ADR-DEL-002で決定された通り、画像ファイルは削除せずDrive内に保持されます。誤削除時の復元性担保や他アルバムでの共有破壊防止という明確なトレードオフに基づく妥当な判断であり、現時点での技術的負債ではありません。
- **スプレッドシートデータ行数に関するスケーラビリティ**:
  - アトミック一括置換方式により、数千トラック規模の通常運用においてGAS実行時間は1〜2秒程度で完了します。GASの実行時間上限（30秒〜6分）およびメモリ上限（数百MB）に対して十分な安全マージンがあります。

### 4.3 [改善提案 / Suggestion] (リリース阻害要因ではない)
- **[SUGGESTION-001] 将来の運用に向けた未参照アートワーク画像クリーンアップバッチの検討**:
  - **内容**: ADR-DEL-002の方針に基づき、削除されたアルバムのアートワーク画像はGoogle Drive上に保持されます。日常利用において容量逼迫の懸念は極めて微小ですが、将来的に長期間の運用で多数のアルバムが登録・削除された場合、スプレッドシートから参照されていない孤立ファイルがDrive内に蓄積する可能性があります。
  - **推奨策**: 将来のメンテナンス機能（保守ツール）として、スプレッドシート全行で参照されているURLリストとDriveフォルダ内のファイル一覧を突き合わせ、孤立した未参照画像を一覧表示・一括ゴミ箱移動できる「未参照画像クリーンアップバッチ」の導入を長期的な検討課題とすることを提案します（現時点での本機能のリリースを阻害するものではありません）。
- **[SUGGESTION-002] 大規模データ（数万トラック）を見据えた将来のスケーラビリティ検討**:
  - **内容**: 現在の数千曲規模ではアトミック一括置換（全行読込・全行書き戻し）が最速かつ最適ですが、万が一カタログが数万行〜数十万行規模に成長した場合、スプレッドシートの読込・書込時間が増加する可能性があります。
  - **推奨策**: カタログ規模が将来的に1万行を超えるようなエンタープライズ運用を行う場合は、シートの年度別・アーティスト別分割や、削除済みフラグによる論理削除＋定期バッチアーカイブへの移行をアーキテクチャの進化フェーズとして検討することを推奨します。
